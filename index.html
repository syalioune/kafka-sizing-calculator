REST Proxy is stateful for consumption — a consumer group instance is created on one proxy and subsequent fetch requests for that consumer must be routed to the same instance (sticky sessions). Producing is stateless. CPU-bound due to JSON serialization/deserialization. Memory is needed for consumer state, connection pools, and request buffering.

Topology
ms round-trip
Stretch Cluster: A single Kafka cluster where broker.rack distributes replicas across DCs. Every produce with acks=all waits for cross-DC acknowledgment. This guarantees RPO=0 (zero data loss) and strong data consistency — all consumers in every DC see the exact same data, with no divergence or conflict resolution needed.

Latency tradeoff: produce latency increases by the inter-DC RTT. This is often acceptable for event-driven architectures, batch consumers, and workloads that prioritize correctness over low-latency produce. Tuning linger.ms and batch sizes can amortize the overhead.

📄 broker.rack · 📄 min.insync.replicas

Stretch Cluster Sizing
Stretch Cluster
Multiple Clusters: Each DC runs an independent Kafka cluster with its own RF internally. Data is replicated asynchronously via MirrorMaker 2 or Confluent Cluster Linking. Produce latency is purely local.

Consistency tradeoff: Asynchronous replication means RPO>0 — data loss is possible on DC failure. In active-active setups, consumers in different DCs may see different data at any given time, message ordering across origins is non-deterministic, and data divergence can occur. For use cases requiring strict consistency (financial transactions, inventory management, regulatory data), this may necessitate complex application-level conflict resolution.
